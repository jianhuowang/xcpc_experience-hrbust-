# 投稿 Schema

## 什么值得共享

EXP 收录能帮助其他成员识别问题、采取行动并检查结果的经验。可以从一道题或一次失误开始，不要求新算法、难题或多次 AC；`single-case` 是合法证据级别，但不能据此宣称普遍有效或协会共识。

起草前回答四个问题：

1. **可复用结论**：去掉题号和个人情绪后，还能说清“遇到什么信号，采取什么做法，为什么”吗？
2. **实际依据**：来自哪道题、哪次编译/提交、推导或来源？区分已经执行的验证、仅手推和尚未验证；单次 AC 不等于证明所有适用情形。
3. **适用边界**：依赖什么条件，哪些情形不能照搬？没有构造出反例时如实说明，不能伪造反例或把边界写成“任何情况”。
4. **相对增量**：已有经验是否包含同一结论？新案例通常补入旧条目，不因换了题目就另起一篇。

| 内容 | 建议 |
|---|---|
| “这道题很巧，要多思考、多练习”或只有 AC 代码/完整题解 | 先留在个人复盘；提炼具体识别信号、原理和可执行动作后再投稿 |
| 一次编译失败，确认根因、环境条件，并复现修复结果 | 可用 `single-case` 投稿；已有同类结论则补证据 |
| 由具体题目提炼出的模型、不变量或调试方法，能说明迁移条件 | 可投稿；不要求方法原创，引用原来源并说明自己的经验增量 |
| 比赛分工或训练感受，有具体事件、因果分析及下一次可验证的动作 | 可按 `contest/team/training` 整理；未完成的实验如实记为未验证 |
| AI 给出的漂亮总结，但投稿者无法核对来源、推导或验证 | 标注缺失依据；可整理已有材料的待补草稿，不包装成可提交的 active 条目 |

“资料不足”与“不值得共享”不同：前者补依据，后者留个人记录。篇幅与术语数量不是质量门槛；公共章节简短但具体即可，不为填表编造内容。最终仍由 PR 人工审核技术正确性与复用价值。

## 两层审核与证据边界

第一层由投稿 Agent 初筛，按上述四个问题给出：已查范围与相关 ID、重叠内容、实际增量、证据来源与未核实事项，以及“新建 / 更新 / 不投稿 / 待补材料”的建议。需要判断增量时阅读候选正文；受盲做权限限制不能读取时，明确比较未完成，不把标题相似当作完成查重。

第二层由 PR 人工审核技术正确性、来源可信度、适用边界及是否收录。Agent 的建议不是审核通过，CI 只检查结构和确定性规则，不替代内容审核。

- **模拟材料**：用户声明模拟、虚构或角色扮演时，输出开头和修改草稿紧邻处注明“模拟草稿，不可直接入库”；模拟身份、验证结果不得作为实际作者或真实证据。只有另行提供真实材料后才能整理正式投稿。单纯“只读测试”不意味着材料虚构，不能混淆操作限制与证据真实性。
- **用户自述**：真实投稿中，未独立核对的经历写成“据 @用户名 自述”，明确哪些提交记录、日志或条件尚未核实；没有链接不自动否定单次经验，也不得伪造链接、日期或声称维护者已复核。实际运行、已查原始记录与独立推导分别标注。
- **因果强度**：切换评测选项后通过，可以说“与原结论一致”。若未确认代码不变、完整编译环境及其他差异，不能称为严格控制变量验证或排除其他原因；需要更强归因时先补这些信息。
- **证据等级**：`single-case` 表示单次案例，`repeated-practice` 表示多次实际实践共同支持同一结论，`source-backed` 表示可核对来源支持结论，`team-consensus` 表示有真实团队共识记录。根据实际证据范围选择，不按人数或次数自动升级，也不以缺少固定次数阈值为由拒绝评估新增证据；升级或保留都说明依据，未核实部分交 PR 审核。

## 文件名

新条目使用 `short-title.md`，例如 `trie-lcp-count-contribution.md`，不添加日期或作者前缀；文件名去掉 `.md` 后即稳定条目 ID。旧条目保留原文件名（包括已有 `YYYYMMDD-author-` 前缀），不为统一格式重命名。

`short-title` 使用小写英文、数字和单连字符，表达主题与核心结论，不用泛名或版本号区分重复投稿。重名时先判断是否应更新旧条目；确实不同再细化名称。正文一级标题使用清晰的人类可读中文，不加入作者或日期。作者只写 `authors`，实际修改日期写 `updated`；创建后不随这些字段或标题变化改 ID。

网页 MCP 检索使用 ID、标题和 topics 元数据，并非只按文件名搜索，也不搜索正文全文。文件名表达核心主题，标题保留自然中文术语，topics 填相关英文主题词；不要为了增加检索词而改旧 ID。本地 Agent 还可以按 Skill 检索正文。

通常直接在知识目录新增文件。校验与打包也支持子目录，但整棵知识目录中不能有同名 Markdown，避免稳定 ID 重复；来源链接保留子目录路径。

## Frontmatter

```yaml
---
kind: algorithm
topics: graph, shortest-path
evidence: repeated-practice
authors: "@alice"
status: active
updated: 2026-09-02
related:
---
```

- `kind`：`algorithm / implementation / debugging / contest / team / training`
- `evidence`：`single-case / repeated-practice / source-backed / team-consensus`
- `status`：`active / deprecated`
- `topics`、`authors` 可用英文逗号分隔多项
- `topics` 至少一项，每项使用小写英文/数字 kebab-case（如 `fenwick-tree`、`x86-64`）；不得重复或出现空项
- `authors` 至少包含一位投稿者，并使用 GitHub `@用户名`
- 审核人与合并人不写入条目；GitHub PR approvals、CODEOWNERS 和 merge history 是唯一审核审计来源
- `related` 可省略、留空或填写逗号分隔的稳定条目 ID；目标必须是当前知识目录中存在的其他条目，不得指向自身，可以关联 deprecated 历史

Frontmatter 使用单行 `key: value`，值可加单引号或双引号；同一字段不得重复。不支持多行、嵌套 YAML。

不要猜造 `type: experience`、`status: draft` 或 `topics` 的 YAML 列表。类型字段是 `kind`，稳定 ID 来自文件名，不另加 `id` 字段。聊天中的“草稿”是工作进度，不是可填写的 `status` 值；材料不全时按以下交付规则提供待补稿。

## 投稿交付格式（网页与本地 Agent 共用）

默认分两阶段：先给完整初稿供用户审阅，用户确认或修改后再输出最终稿与 PR 信息。用户已经审阅或明确直接要最终稿时，不重复索取正文确认。个人复习卡、算法讲解或空模板不能代替稿件。

**第一阶段：初稿。** 简述已查范围、相关 ID、重叠与增量和处理建议，再给目标路径、主题文件名及含全部必需章节的完整初稿。已有材料能确定的内容直接填好；更新旧条目优先最小补丁，保留 ID、原作者和已有证据。无可复用内容或无增量时说明不投稿理由，不制造文件。

- 未知 `authors:`、`updated:` 等元数据保留空值，不填假姓名、占位用户名或“待补充”字符串；已有信息直接采用。来源或验证完全没有真实材料时，保留章节标题并留空，不用模拟 AC 填充。若已有部分依据或真实自述，则如实填写该部分，不要求必须有提交链接。
- `updated` 是稿件实际修改日期，不是做题、AC 或证据发生日期。本次正在起草或修改，且用户提供或可靠会话/系统上下文已给出当前日期时，直接填入对应的 `YYYY-MM-DD`，无需再问；用户要求留空或指定实际修改日期时按其要求。没有可靠日期时才留空，不从示例、知识库 revision 或旧文件名推测今天。仅查询或原样转发旧条目时保留其原日期，不刷新历史记录。
- 只将尚缺的信息和影响正确性的疑问集中列在稿件外，不重复追问已知信息。缺身份、日期或链接不阻止出初稿；关键条件未确认时，正文仍须保留条件假设、用户自述、独立推导或尚未验证等必要限定，不为“干净”而把猜测写成事实。
- 稿件外简短说明仍需补齐的必填项与实际校验状态，模拟提醒也放在代码块外。正文不反复叙述“这是模拟验收”，更不能把模拟身份、经历当成真实贡献。初稿只在聊天或用户明确指定的草稿位置保存，不自动写入知识目录。

**第二阶段：最终交付。** 根据审阅意见整理正文，单独给文件名与目标目录；完整 Markdown 放在单个四反引号代码块中，保留内部三反引号代码块。Frontmatter 每行一个字段，公式只输出单份源码，面向 GitHub 优先使用 `$...$` 和 `$$...$$`。PR 标题及按仓库模板填写的描述放在稿件代码块外，保持复选框 `- [ ]` / `- [x]` 语法。最终稿不要夹带流程说明或个人训练卡。

用户决定自行填写的字段可以继续留空，稿外集中提醒补齐；“最终交付”不等于必填项齐全或校验通过。未执行的检查直接写“未运行”，不写“已通过——未实际执行”，不勾选通过。正文确认只代表认可内容，不授权发布；只在用户明确授权时执行 commit、push、创建或合并 PR，手动投稿使用投稿分支到 main。

草稿中的 `status: active` 仅演示目标格式，不代表已审核。空字段、空章节或占位稿仍由现有校验器拒绝，不放宽正式投稿要求。

### 正文长度与章节职责

一般正文以 500～1000 字为软目标，不计代码、公式和来源；简单经验可更短，复杂经验可更长，不增加 CI 字数限制。不得为凑字数补废话，也不能为了压缩而删除必要条件和证据。

结论讲做法，信号讲何时想到它，原理讲为什么，验证讲实际证据，边界讲何时不能用；核心模型保留关键状态或不变量，实现风险讲代码细节，迁移识别讲换题后的判断。保留对应 kind 的全部必需章节，普通章节通常 1～3 句即可，必要证明不受此限制。

**相同观点只集中解释一次。** 将完整解释、证明或反例放在最适合的一节；其他章节可用一句结论承接或引用该节，不换措辞重复展开。同一公式的必要定义或引用不算重复。提交初稿及最终稿前自行检查跨章节重复，直接精简稿件，不附冗长自查报告。

压缩时保留算法适用条件、证据性质和复杂度假设。例如状态扩展最短路应区分单位边权 BFS、0/1 边权的 0-1 BFS、非负边权 Dijkstra；复杂度需说明每个状态的转移数量、计算代价，以及空间是否包含原图或显式扩展边，不能为缩短正文省掉这些前提。

## 如何选择 kind

| kind | 主要可复用结论 |
|---|---|
| `algorithm` | 跨题复用的算法模型、识别信号和不变量 |
| `implementation` | 语言、模板、数据结构实现和工程细节 |
| `debugging` | 错误症状、定位路径、根因与修复验证 |
| `contest` | 具体比赛中的技术、信息和现场决策复盘 |
| `team` | 可跨比赛复用的分工、沟通和协作机制 |
| `training` | 能力缺口、训练动作、完成标准和复测证据 |

跨多个类型时，以主要结论选择一个 `kind`，不要复制成多个近似条目。

## 更新与生命周期

- 投稿前检索并阅读相关条目，说明已有 ID、重叠内容、新增价值和处理建议；可以直接采用投稿 Skill 生成的对比摘要。已有相同结论且没有新增信息时引用原条目，无需创建投稿。
- 修正文案、来源，或为同一结论补充案例、证据和边界时，更新原条目并修改 `updated`。保留稳定 ID、原作者和未涉及的正文，按实际贡献补充 `authors`，不要整篇替换丢失旧证据。
- 可独立引用的新结论或需要独立说明的不同问题，创建新条目并用 `related` 关联已有经验；仅换题目、表述、标签或增加一份相同结论的证据不构成独立条目的理由。
- 新证据与旧结论冲突时先并列证据和适用条件，交由审核者核实；确认推翻后再将旧条目标为 deprecated，新建或更新替代条目，并相互关联。
- 投稿分支可填写 `status: active`，但只有通过 PR 审核合并进 main 后才作为已审核协会经验。结构校验不代替人工内容审核。
- deprecated 条目保留历史，默认不用于查询，也不进入普通 Chat 知识包；不要为了清理目录直接删除被引用条目。

`npm run validate` 会拦截全库 active 条目的确定性正文重复：忽略 Frontmatter、开头一级标题、CRLF/LF 和首尾空行，保留正文内部空白、代码、数字、来源与证据。报错会列出重复双方的 ID。deprecated 历史不参与此项拦截；通过校验不表示没有语义重复，换一种表述或来源即可超出确定性检查的能力。

## 公共正文

每个章节必须有实际内容：

```markdown
# 标题

## 经验结论
## 适用信号
## 常见 blocker 或失败症状
## 原因与原理
## 验证方式
## 边界与反例
## 来源
```

`来源` 至少一项；外部链接必须使用 HTTPS。

active 条目的任一必需章节都不能以 `TODO`、`TBD`、`待补充` 或 `替换为` 开头。deprecated 示例允许保留模板占位文本。

## 类型扩展

| kind | 额外必需章节 |
|---|---|
| `algorithm / implementation / debugging` | `核心模型或不变量`、`复杂度与约束`、`实现风险`、`迁移识别` |
| `contest / team` | `技术层复盘`、`团队信息层复盘`、`现场决策层复盘`、`应保留的做法`、`下一次实验` |
| `training` | `暴露的问题`、`训练动作`、`完成标准`、`复测结果` |

算法类条目可另加 `H1`、`H2`、`H3`，分别保存方向、关键观察和完整解法。

## 完整起草骨架

下面是 `algorithm` 的结构模板，也适用于 `implementation/debugging`（修改 `kind`）。其他类型保留公共正文，按“类型扩展”表替换最后四节。所有占位内容都必须由真实材料替换；这份空模板不能提交，也不表示校验通过。作者、日期、来源、验证和 related 均不得猜填；模板不要求加入可选的 H1/H2/H3。

建议文件名：`short-title.md`，补齐后保存到 `.agents/skills/xcpc-experience-coach/references/knowledge/`。

```markdown
---
kind: algorithm
topics: topic-name
evidence: single-case
authors:
status: active
updated:
related:
---
# 待补充：清晰的经验结论标题

## 经验结论
待补充：满足什么条件时，应该采取什么做法。

## 适用信号
待补充：怎样识别本经验适用的问题。

## 常见 blocker 或失败症状
待补充：具体卡点、错误或失败表现。

## 原因与原理
待补充：为什么有效；区分推导、观察和猜想。

## 验证方式
待补充：实际已做的验证及结果，尚未验证的部分明确说明。

## 边界与反例
待补充：成立条件、不能照搬的情况或尚未确认的边界。

## 来源
待补充：真实来源；外部链接使用 HTTPS。

## 核心模型或不变量
待补充：关键结构与正确性理由。

## 复杂度与约束
待补充：时间、空间及适用规模；不适用时解释原因。

## 实现风险
待补充：实现时需要核查的细节。

## 迁移识别
待补充：遇到另一道题时怎样识别并使用这个结论。
```
